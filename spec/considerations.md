# Considerations: open problems and current workarounds

Every known unsolved problem, accepted limitation and workaround in the engine, each stamped with the milestone and plan step it belongs to (`M3 · F3` = milestone M3, [PBR plan](./pbr_implementation_plan.md) step F3). A new problem or workaround is added here when it is found. A solved one moves to **Resolved** with its date and fix. M8 optimization, lighting-bias, stability, floor-tier, and perf tuning findings are tracked in [m8_optimization_and_fixes.md](./fixesM1-6/m8_optimization_and_fixes.md) (and RTX Mega Geometry items in [mg_optimizations_fixes.md](./fixesM1-6/mg_optimizations_fixes.md)) rather than duplicated here.

Kinds:
- **Workaround:** code that works around a defect elsewhere, usually a library. It stays until that defect is fixed.
- **Limitation:** a known gap in what is built.
- **Deferred:** scheduled for a later step.
- **Unverified:** not yet measured or tested.
- **Warning:** a validation message that is not fixed.

## M2 · C4 PTLAS

- **C-C4-3 · Workaround · the OMM ray flag's SPIR-V capability is declared by hand.** Slang 2026.20 emits `RAY_FLAG_FORCE_OMM_2_STATE` (`0x400`) without `OpCapability RayTracingOpacityMicromapEXT`, and spirv-val rejects the module. `requireOmm2StateRayFlag()` in `shaders/raytracing/trace.slang` declares `SPV_EXT_opacity_micromap` and the capability through `spirv_asm`; `traceVisibility` and `traceClosest` call it, and every new ray (the G1 SER trace) must too. Upstream: [shader-slang/slang#13438](https://github.com/shader-slang/slang/issues/13438), open, milestone Q4 2026; a contributor's comment of 2026-10-16 reports this exact gap (also for `RAY_FLAG_SKIP_TRIANGLES`), reproduced on master. No maintainer decision on KHR vs EXT or on when the capability is declared, and no PR for it (2026-11-18). The issue's main topic, the `OpacityMicromapIdKHR` execution mode of `VK_KHR_opacity_micromap`, does not apply: the engine enables `VK_EXT_opacity_micromap`. 2026-11-18: the workaround is accepted as is; it works and uses Slang's own OMM ray flag, only the declaration is by hand. **Exit:** #13438's ray-flag part fixed in a Slang release, then spirv-val clean with `requireOmm2StateRayFlag()` removed; if Slang settles on the KHR capability, check that an EXT-only device still gets a valid module. Re-check with spirv-val on every Slang upgrade.

## M3 · F1 RTXDI host context

- **C-F1-1 · Limitation · reservoir contents are undefined after a resize.** Correctness relies on the resize arriving as a camera cut, which resets history so the shade pass skips reuse for that frame. **Exit:** none needed while resize keeps resetting history. Recheck if the history-reset rules change.

## M3 · F2 RTXDI bridge

- **C-F2-2 · Workaround · RTXDI's implicit `uint`→`bool` warning (E30081) is disabled for each whole compile unit.** Units that include the bridge compile with `RTXDI_SLANG_FLAGS` (`-warnings-disable 30081`). Slang 2026.20 ignores `#pragma warning` scoping once a unit imports a module, so the warning cannot be limited to RTXDI's headers. RTXDI 3.2 still has the conversion: 8 warnings in `TemporalResampling.hlsli`, `SpatialResampling.hlsli` and `Utils/Math.hlsli` (2026-11-15). **Exit:** a Slang version that scopes the pragma, or an RTXDI version without the conversion.
- **C-F2-3 · Limitation · the `DirectionalLight` sample asset cannot serve as a shadow-acne test.** Its spheres are wound inside out on single-sided materials, so its `Shadowed lights` view is black by design. **Exit:** use another asset for acne checks.

## M3 · F3 ReSTIR DI passes

- **C-F3-1 · Workaround · bounds-checked reads in the bridge.** RTXDI reads its buffers as structured buffers under robust access, where out-of-range reads return zeros:
  - the fused pairwise path loads the reservoir of an off-screen back-projected pixel;
  - it loads light 0 for an empty result, even when no lights exist.

  Through BDA both reads lost the device. The bridge's reservoir accessor and `RAB_LoadLightInfo` now check bounds. RTXDI 3.2 (2026-11-15) dropped the fused path and guards the empty result in `RTXDI_TargetPdfHelper`, but still assumes robust buffers, so the checks stay. **Exit:** none expected. Any new RTXDI bridge (ReSTIR GI in G5, PT) must do the same.
- **C-F3-5 · Deferred · no environment light.** Emissive triangles exist since M7 E2 (2026-11-20); local lights are presampled since M7 F1 (2026-11-21, [f1_light_presampling.md](./m7/f1_light_presampling.md)). `lightPresent` stays 0, so RTXDI never reaches the bridge's environment functions, and the RIS buffer's environment segment (131,072 entries, 5.0 MiB with its compact rows) is allocated unused. **Exit:** unscheduled.

## M3 · H1 DLSS Ray Reconstruction

- **C-H1-1 · Workaround · NGX needs the driver's descriptor heap.** NGX's kernels address images by `VK_NVX_image_view_handle` handles, which index the driver-managed descriptor heap. While the engine's `VK_EXT_descriptor_heap` heap is bound, they index that heap instead. DLSS-RR then reads and writes whatever image sits in the engine slot with the same number: a guide image was overwritten every frame (motion test 6 of 13), and with the reserved range moved to the heap start the output stayed black. A new command buffer does not reset this. `Dlss::evaluate` binds an empty legacy descriptor set (`vkCmdBindDescriptorSets2` with a one-set pipeline layout) right before the evaluation, which returns the driver to its own heap. DXVK does the same (`DxvkContext::launchCuKernelNVX`, "no spec-legal way to bind it"). DXVK's bind without a layout crashes driver 621.01 inside `nvoglv64.dll`. The renderer rebinds both heaps afterwards. **Exit:** a spec-legal way to select the driver heap, or an NGX that does not use image view handles.
- **C-H1-2 · Warning · NGX's own validation messages.** These come from inside `NGX_VULKAN_EVALUATE_DLSSD_EXT` and pipeline creation, with no engine command in between:
  - `SYNC-HAZARD-WRITE-AFTER-WRITE` twice, on the first evaluation after each feature creation. NGX transitions two of its own images (`nv.ngx.dlssd.resource`) and then clears them without a barrier. NVIDIA's developer forum has a report of the same clear.
  - `BestPractices-SpirvDeprecated_WorkgroupSize` three times, from NGX's compute pipelines.
  - `BestPractices-NVIDIA-BindMemory-NoPriority` 54 times and `BestPractices-vkBind{Buffer,Image}Memory-small-dedicated-allocation` 28 times, at feature creation: NGX allocates each `nv.ngx.dlssd.resource` (64 B to 23 MiB) with its own `vkAllocateMemory`, without a priority, and names it only after the bind (an API dump on 2026-11-21 maps all 54 allocations to it). NGX's allocation callbacks (`NVSDK_NGX_Parameter_ResourceAllocCallback`) exist for D3D11 and D3D12 only.

  The other per-frame hazard, NGX's fills against the previous evaluation's writes, is fixed by the engine's barrier before the evaluation. **Exit:** a DLSS SDK that fixes them.
- **C-H1-3 · Workaround · `--wrap=malloc` and MSVC-built static libraries.** The engine's modules link with `--wrap=malloc/calloc/realloc/free/aligned_alloc` to route allocations to mimalloc. `nvsdk_ngx_d.lib` is MSVC `/MD` code and calls `malloc` and `free` through `__imp_malloc` and `__imp_free`. lld redirects those to `__imp___wrap_*`, and its fallback local import left all 9 call sites with a zero displacement (crash in `NGXGetPathUsingQAI`). `src/util/mi_new_delete.cpp` defines the `__imp___wrap_*` slots, and that object is compiled without LTO, since bitcode slots did not resolve either. Checked with clang 22.1.8's lld. **Exit:** drop `--wrap`, or an lld that resolves the fallback.
- **C-H1-6 · Limitation · the debug views are not upscaled.** A debug view writes the display image at render resolution, and the DLSS-RR evaluation is skipped, so returning to Lit resets its history. **Exit:** none planned; debug views show render-resolution data on purpose.

## M3 · E3 engine sun

- **C-E3-1 · Limitation · the startup view gets no direct sun.** The startup camera looks at the origin from the +Z gallery, under the arcade roof and behind the curtains. A sweep of 18 sun directions lit at most 0.6% of that view, so Lit started nearly black before M4. Since M4 G6 (2026-11-19), indirect bounce lights the gallery walls and pillars (dim at EV 0, clearly lit under auto exposure / +3.6 EV, [g6_combine.md](./m4/g6_combine.md) §3). The camera was left where it is, because the bench and the timing history in engine spec §2.3 use that pose. **Exit:** accept the bounce-lit gallery pose, or switch to a courtyard startup pose with the bench history re-baselined.
- **C-E3-2 · Limitation · DLSS-RR quality depends on jitter and mode.** On the sunlit courtyard with a still camera, the temporal deviation of the Lit output is 0.35% of the mean at Quality and 0.31% at Performance, but 0.88% at DLAA (8 jitter phases), and 8.7% at Quality with the `Jitter` checkbox off: RR needs the jitter. **Exit:** none planned; the checkbox stays a debug control.

## M3 · H2 post

- **C-H2-1 · Limitation · the color is not pre-exposed.** `GpuFrameRoot.exposure` and DLSS-RR's `InPreExposure` stay 1. NGX takes pre-exposure as a CPU float, which would need the GPU exposure read back a frame or more late. The RGBA16F `noisyColor` had enough range on the test scenes. **Exit:** a scene whose radiance nears the FP16 limits (65504 at the top), then pre-expose by a read-back value.

## M4 · RTXDI 3.2 update

Stamped M4, the current milestone; [rtxdi_3_2_update.md](./features/done/rtxdi_3_2_update.md).

- **C-R32-2 · Limitation · temporal reuse has no Pairwise MIS.** 3.1's fused pass applied Pairwise MIS to its temporal sample too; 3.2's temporal pass offers `Off`, `Basic` and `Raytraced` only. On `LightsPunctualLamp` the frame-to-frame change rose from 0.76% to 1.50% and the per-frame error from 4.20% to 4.75%. ## M4 · G1 SER pipeline

- **C-G1-1 · Workaround (shelved with SER, C-G1-3) · the closest-hit reads `ClusterIDNV` through `spirv_asm`.** Slang 2026.22 has no `ClusterID()` intrinsic for SPIR-V hit shaders, and `HitObject::GetClusterID` is NV-only (no EXT target). `writeClusterPayload` in `shaders/raytracing/ser.slang` loads the builtin directly, declaring `SPV_NV_cluster_acceleration_structure` itself. Probed 2026-11-16, `spirv-val` clean. **Exit:** a Slang intrinsic for the hit-shader cluster id, or `GetClusterID` on the EXT path, which would also drop the closest-hit invoke.
- **C-G1-2 · Workaround (shelved with SER, C-G1-3) · no subgroup operations after `ReorderThread`.** On driver 621.01 (RTX 5070), wave ops after a reorder in raygen go wrong: a reorder followed by `WaveActiveCountBits` + `WaveIsFirstLane` counted 13,098,546 of 13,102,080 launches, and the same counters after `HitObject::TraceRay` + `ReorderThread` lost the device. The SPIR-V is in the right order (`OpReorderThreadWithHintEXT`, then `OpGroupNonUniformBallot`); per-lane atomics after the reorder are exact. `rt_ser_check.slang` counts with one atomic per lane. Every SER raygen must avoid subgroup ops after the reorder (G2, G3 update paths). Not yet ruled out: descriptor heaps (every bisect variant used a heap pipeline). The Vulkan beta driver branch (597.33, 2026-10-22: descriptor-heap stability and untyped-pointer fixes) is separate from the Game Ready branch (621.01) and may carry fixes 621.01 lacks; none of its notes names SER or subgroups. RTXGI 2.9.0's IndirectDiffuse sample does what this forbids: on Vulkan it traces with `VK_NV_ray_tracing_invocation_reorder` (`OpReorderThreadWithHitObjectNV` + `OpHitObjectExecuteShaderNV`, DXC) and then calls `NrcUpdateOnHit` in raygen, whose `NrcIncrementCounter` uses `WaveActiveCountBits` / `WavePrefixCountBits` / `WaveReadLaneFirst`. So wave ops after a reorder work there, with the NV extension, descriptor sets and DXC. **Exit:** with SER restored (C-G1-3), test the Vulkan beta driver and recheck on each driver update, both branches, with the recipe in spec/m4/g1_ser_rt_pipeline.md §7, and report to NVIDIA with a standalone repro. No non-heap variant: descriptor heaps are the binding model (decided 2026-11-17).
- **C-G1-3 · Deferred · SER shelved.** On 2026-11-17 the user shelved SER (the EXT path): Slang's EXT `HitObject` support is incomplete: [#12554](https://github.com/shader-slang/slang/issues/12554) (`GetRayTCurrent` missing on SPIR-V), [#13763](https://github.com/shader-slang/slang/pull/13763) (EXT SER wrappers need an explicit capability), [#13772](https://github.com/shader-slang/slang/issues/13772) (wrong hit-query capabilities), [#13774](https://github.com/shader-slang/slang/issues/13774) (no fused trace-reorder-execute on `HitObject`). The indirect pass and the NRC update paths are compute shaders that trace with `traceClosest` (`passes/indirect.slang` `indirectMain`, `passes/nrc_update.slang` `nrcUpdateMain`). Kept in the tree, not built: `shaders/raytracing/ser.slang`, `shaders/checks/rt_ser_check.slang` (its `CMakeLists.txt` line commented out; moved from `passes/` by checks_dll CK3), `src/render/vk_rt_pipeline.{hpp,cpp}` (out of `src/render/CMakeLists.txt`); each carries a SHELVED header. The `GpuSerCheckStats` / `SerCheckPushData` mirrors and their layout tests stay, so the shelved shader still matches. Removed: the SER check's renderer and ray-check wiring, its timer scopes, `IndirectPass`'s pipelines and the UI reorder toggle (commits `3af7f2052` G1 and `8b4e87bf3` G2 hold them). The device still enables `VK_EXT_ray_tracing_invocation_reorder` and the RT pipeline features, unused. Effects: GPU-AV now runs the indirect and update passes clean (C-G2-2 is moot); NRC's counter is back to one atomic per wave (C-G1-2 is moot); the update pass fell from 0.18 to 0.017 ms (no fixed trip count of NOP traces). **Exit:** engine spec §16.5 V1 (post-1.0): with the four Slang issues fixed in a pinned Slang, SER returns as a toggle beside the ray-query passes, with its check (bit-identical to `traceClosest`) and reorder on/off timings; expected to become the default.

## M4 · G2 indirect pass

- **C-G2-2 · Open (shelved with SER, C-G1-3: the compute indirect pass runs GPU-AV clean) · GPU-AV loses the device on the SER indirect pass.** On driver 621.01 (RTX 5070, SDK 1.4.363 layers), GPU-AV with BDA bounds instrumentation (`gpuav_buffer_address_oob`) loses the device on the first frame that records `indirect.slang` ("Failed to wait for fence", nvlddmkm event 153). Bisect, 2026-11-16, by `.spv` swap:
  - clean: shader instrumentation off; BDA OOB check off; the indirect pass skipped (G1's SER check stays GPU-AV clean);
  - clean: the same shading code with `traceClosest` (ray query) instead of `traceShaded`, which also gives full GPU-AV coverage of the decode, material and light loads with no reports;
  - clean: `traceShaded` followed by one BDA load;
  - device lost: `traceShaded` followed by `decodeHit` alone; with reorder off (no `ReorderThread`); with GPU-AV safe mode on (which skips failing accesses, so a real out-of-bounds access is ruled out); with GPU-AV's check functions inlined; with an `-O2` shader.

  The engine runs it clean without GPU-AV, and the SER check proves its hits bit-identical to `traceClosest`. Likely the same driver area as C-G1-2: code after `HitObject` trace + invoke in raygen. Until fixed, the GPU-AV pass for SER raygens is the `traceClosest` variant. **Exit:** GPU-AV runs `indirect.slang` clean on a driver update (both branches); report with C-G1-2.

## M4 · G3 NRC

- **C-G3-3 · Workaround · the NRC SDK leaks Vulkan objects.** `nrc::vulkan::Context::Destroy` and `Shutdown` leave objects alive, and every `Configure` (it reloads the network: "Loading the default network config data") leaks more. `VUID-vkDestroyDevice-device-05137` breakdown (NRC 0.16, 2026-11-17):
  - per context: 13 `VkCuModuleNVX`, 8 `VkCuFunctionNVX`, 1 descriptor pool, 4 sets, 1 set layout, 1 pipeline layout, ~8 buffers with their memory;
  - per `Configure`: 1 fence, 4 `VkCuFunctionNVX`, ~1 buffer with its memory;
  - before the workaround, SDK-allocated buffers leaked as well: 92 objects after one resize.
  - in `Context::Create`, one 144-byte uniform buffer in its own 192-byte allocation, unnamed and without a priority (`BestPractices-vkBindBufferMemory-small-dedicated-allocation` and `-NVIDIA-BindMemory-NoPriority` once each; found in the 2026-11-21 API dump). `enableGPUMemoryAllocation = false` does not cover it.

  Workarounds (2026-11-17): the engine allocates the SDK's buffers (`enableGPUMemoryAllocation = false`, VMA, named) and frees them itself, and the configured frame only grows, so a resize to a smaller extent never reconfigures. The motion test (with its resize) now ends at 51 leaked objects; the guide capture, which reconfigures for every shot's bounds, at 116 after 10 configures. Engine objects are all destroyed before the device. **Exit:** an SDK update that frees them; recheck with each NRC upgrade.
- **C-G3-4 · Limitation · no training loss on Vulkan.** `QueryAndTrain` with a loss pointer returns status 4 on Vulkan: tiny-cuda-nn's `cudaMemcpyAsync` of the loss reports "operation not supported" (NRC 0.16, driver 621.01). The engine passes `nullptr`, so there is no loss plot and no loss UI. The "loss falls after load" check is replaced by the cache view's convergence (spec/m4/g3_nrc.md §3). **Exit:** an SDK version that reads the loss back on Vulkan.
- **C-G3-5 · Limitation · `requestReset` does not reset the network.** `Configure` with `requestReset` leaves the learned weights in place: the cache view's mean was 0.000367 before and 0.000370 after a reset at frame 300 (2026-11-17). The engine has no cache reset; a new scene layout reconfigures the bounds but keeps training from the current weights. 2026-11-19 (G6): a scene switch shows stale light. In the guide capture, `MetalRoughSpheres` (no lights, no emission) loaded after lit shots has nonzero `NRC cache` on 9% of the pixels and nonzero `Indirect radiance` on 6% (max 0.18 in the 8-bit PNG) a few frames after the load, and the combine now passes it to `Lit`. How long training takes to remove it is not measured. **Exit:** a reset that works (SDK update, or destroy and recreate the context, against C-G3-3's leaks and G7's never-destroyed rule) if a scene switch shows stale light for long enough to matter.
- **C-G3-6 · Workaround · queue work or SDK calls during NRC / DLSS-RR work lose the device.** On driver 621.01 (RTX 5070, NRC 0.16), uncapped release runs lost the device (`waitForFences: ErrorDeviceLost`).
  - 2026-11-17, render 853×480: after about 650 frames, every run of ≥700 frames; runs that waited for the device every frame (the probe captures) never did. Bisect, 4 runs of 1500 frames each:
    - lost: baseline; update paths and resolve skipped (`QueryAndTrain` alone is enough); SDK `maxNumFramesInFlight` 3, 4 or 8; `EndFrame` skipped; a full `ALL_COMMANDS` memory barrier at the start of the next frame's command buffer; the next ray submit or frame submit waiting on the previous frame's `rayTimeline` at `ALL_COMMANDS` (GPU side); a host wait placed after the next submit; the frame submit sent before a host wait and the ray submit after it;
    - clean: `QueryAndTrain` skipped; `waitIdle` after every frame; a host wait for the previous frame's `rayTimeline` value before the next frame's graphics submit (the first workaround).
  - 2026-11-18, user report: going full screen (render 1707×913) lost the device within seconds; a 1920×1080 window (render 1280×720) did too, without a resize. The first workaround still sent the present submit and the present right after the NRC ray submit. Bisect at 1920×1080 / 2560×1369, 2–3 runs of 1500–3000 frames each:
    - lost: the present submit waiting on `rayTimeline` GPU side; ray and present in one `submit2` call with the present right after it; also waiting on the host before the next compute submit; waiting on the host only for the NRC commands (split command buffer, DLSS-RR still running) before the present; a deferred present whose next frame records its ray commands (NRC and NGX calls) before the host wait;
    - clean: NRC off; `QueryAndTrain` skipped; DLSS-RR skipped (NRC on); `waitIdle` after every frame; a host wait for the whole ray submit (NRC + DLSS-RR) before the present submit or before the present; the same with a 5 ms sleep after an NRC-only wait.
  - 2026-11-18, SDK calls isolated (requested by the user): NRC `BeginFrame`, NRC `QueryAndTrain` and the DLSS-RR evaluation each record into a primary command buffer of their own, between the engine's command buffers in the same ray `SubmitInfo2` (`FrameSync::kRaySegmentsPerFrame` = 7, `Renderer::recordIsolated`). Each binds the engine heaps before the call and again after it; the C-H1-1 empty set is still bound inside. User report: this fixed the crash. Without the host wait, 0 of 3 runs of 3000 uncapped frames at a 2560×1369 window lost the device; the matching runs without isolation on the same day were not finished.

  So it happens when the CPU issues a submit, a present, or an NRC / NGX recording call while a frame's NRC CUDA kernels (`VK_NVX_binary_import`) or the DLSS-RR evaluation after them still run; GPU-side dependencies do not prevent it, and the window grows with the render extent. Workaround (`Renderer::drawFrame`, `finishPreviousFrame`): the ray commands and the present pass share one `submit2` call; the present is deferred to the next frame, which records its frame commands, waits on the host for the previous frame's `rayTimeline` value, presents, and only then records its ray commands and submits. Swapchain and DLSS rebuilds flush the pending present first. Since 2026-11-18 the NRC and NGX calls also record into command buffers of their own (above); the host wait stays. Cost of the isolation (release, no layers, alternating rounds of 1500 and 6000 frames): none measurable at 1280×720 (GPU total 3.28–3.35 ms and DLSS-RR 1.11–1.13 ms with and without it, frame time 3.89 → 3.82 ms); at a 2560×1369 window GPU total 10.78 → 10.83 ms (+0.5%), the DLSS-RR scope 3.61 → 3.69 ms (+2%), frame time 11.37 → 11.47 ms (+0.9%, inside the ±0.4 ms spread between runs); the other scopes unchanged. Uncapped at 1280×720 a frame takes 3.20 ms (the first workaround 2.87 ms, a host wait right before the present 3.34 ms); 0 of 6 runs of 3000 frames at 1920×1080 and 2560×1369 windows lost the device. RTXGI 2.9.0 (2026-11-12, same NRC commit `7de30e4`) has no such wait: Donut (`e50042f`) keeps 2 frames in flight (`Present` waits only for frame N−2), submits one command list per frame and calls `EndFrame` after it. Its differences: one graphics queue (no async compute), classic descriptor sets instead of `VK_EXT_descriptor_heap` (no C-H1-1 empty set), DXC SPIR-V, and no DLSS-RR after NRC. The heap binding is the likeliest difference; a non-heap repro is ruled out (heaps are the binding model, decided 2026-11-17), so the report to NVIDIA states it as a suspect. That isolating the SDK calls in their own command buffers fixed it points the same way: state recorded in the same command buffer as the CUDA launches. 2026-11-22 (M8 I8, [i8_nrc_cost.md](./fixesM1-6/i8_nrc_cost.md)): host wait disabled by default (`Renderer::isNrcHostWaitEnabled = false`, `ENGINE_NRC_HOST_WAIT=1` fallback kept; `lastNrcRaySubmit` cleared after wait when enabled) after `recordIsolated` alone survived 18,000 uncapped stress frames on driver `621.01` with 0 device losses (`1280×720` Sponza × 3,000, `2560×1369` Sponza × 3 × 3,000, `2560×1369` Sponza `cycle` × 3,000, `2560×1369` Bistro × 3,000), cutting wall `drawFrame` by **−0.560 ms (−13.6%)** at `1280×720`. 2026-11-22, full-screen case (`ENGINE_FULLSCREEN=1`, 2560×1440 desktop, render 1707×960, uncapped `eImmediate`, host wait off, driver `621.01`): Sponza `nrc-restir-gi` × 3, Sponza `cycle` and Bistro `nrc-restir-gi`, 3,000 measured frames each after 240 warm-up: **5/5 exit 0, 0 device losses** (`drawFrame` 11.99–12.02 / 10.33 / 9.37 ms). The previous exit (isolation alone surviving the 2560×1369 run and the full-screen case) is met. 2026-11-25 (M8 · I15 review, MG-P7 in NRC frames): the pre-acquire ray submit now splits at the frame's first SDK segment (`Renderer::recordIsolated`), so NRC frames send their pure-Vulkan `DirectLight` segment in the same `submit2` call as the frame commands ahead of `AcquireImage`; NRC, DLSS-RR and everything after stay with `presentCmd`, and no queue operation or SDK call is added. Driver `621.40`, host wait off, 3,000 uncapped frames each: Sponza at 2560×1369 × 3, Sponza `cycle` at 2560×1369, Bistro `street windows` at 2560×1369, full screen (render 1707×960) and 1280×720: **7/7 exit 0, 0 device losses**. **Exit:** a driver or NRC update that survives without command-buffer isolation (`recordIsolated`) as well; report to NVIDIA with a standalone repro.

## M7 · F1 local light presampling

- **C-F1-3 · Workaround · RTXDI's ReGIR parameters are read through a view.** RTXDI's ReGIR functions take the 1.3 KB `ReGIR_Parameters` by value and index the onion's `layers` and `rings` dynamically. Loaded through BDA, Slang 2026.20 converts the whole struct to its logical layout and every thread keeps it in local memory (`OpVariable Function` arrays of 52 rings and 8 layer groups; `spirv-opt --copy-propagate-arrays` / `-O` do not remove them).
